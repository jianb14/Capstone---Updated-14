# GCash QR Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task-by-task. The user authorized execution in the current workspace.

**Goal:** Replace new PayMongo checkouts with private GCash proof submission and manual merchant verification across booking payments.

**Architecture:** Extend the existing Payment and GCashConfig models and reuse booking/change lifecycle services. Share payment form validation and proof storage between normal and amendment payments; retain legacy PayMongo reconciliation.

**Tech Stack:** Django 5, Pillow, existing Cloudinary SDK, existing HTML/CSS/JavaScript and Playwright.

**Spec:** docs/superpowers/specs/2026-11-12-gcash-qr-design.md

## Global Constraints

- Preserve unrelated user edits and payment history; no hosted migrations or external financial actions. Verified local additive migration requires a validated backup.
- No new dependencies. Follow the existing theme and form/dialog conventions.
- Test with Project.test_settings and its isolated database/storage.

## Review Focus

- A reused reference across different bookings or change requests cannot credit two payments, including concurrent submissions.
- Private proof retrieval cannot expose another customer's files or public storage URLs.
- A late legacy provider payment cannot silently cause duplicate charges or reopen a closed booking.
- Configuration changes do not rewrite the recipient details of submitted payments.
- Rejected proof, expired quotes, and disabled/unconfigured QR retain usable recovery paths.
