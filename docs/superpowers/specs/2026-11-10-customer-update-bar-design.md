# Customer update bar

Approved by the user after reviewing the full-width mockup. Grouping starts at TWO updates, never three.

Show one full-width temporary bar below the navbar on authenticated customer pages while the website is open. One new relevant notification shows a specific message and direct action. Two or more new relevant notifications show "N new updates" and View updates, which opens the existing notification panel. Further arrivals update the same bar, never stack bars. Closing or auto-hiding the bar does not mark notifications as read.

Scope: booking approval/confirmation/decline/cancellation/expiration; payment verification/rejection; change quote ready, changes finalized/declined/expired; admin design delivery (including a revised design delivered through the same flow). Exclude general announcements, chat, concern tickets, self-submission receipts, completed-booking review prompts and payment reminders outside the agreed scope.

Reuse customer-owned Notification records and the existing notification deep links. The repository uses application-generated message patterns rather than notification types; use an explicit conservative allowlist of these patterns and test every included/excluded class. No migration or changes to financial/approval rules.

Bootstrap a signed user-scoped position from the page render. Poll for new records while visible and when returning to the page, retaining the position in per-user session storage across navigation/reload. Initial old unread notifications do not generate a bar. Advance only on successful responses, count all eligible arrivals (including more than a normal feed page), and preserve notification read permissions and CSRF behavior. Poll errors retain the last successful position.

Use the approved thin green success bar for positive single updates, attention styling for rejection/expiration and a neutral grouped bar. Support dark mode/mobile, keyboard and screen-reader access. Do not steal focus, auto-navigate or push the page content when the bar appears. Auto-hide after eight seconds, paused while hovered/focused or the page is hidden. User actions reuse the existing notification read/navigation behavior.

Verify exact 1/2/3 thresholds, filtering/ownership, no duplicates on repeated polls/reload/account navigation, two arrivals when unread count is unchanged, more than 20 arrivals, recovery after failed requests, timer/dismiss behavior, focused typing and customer/admin/guest separation. Inspect screenshots at desktop/mobile in both themes.

Implementation decisions: namespace browser positions by a non-sensitive random login marker so logging out/in starts from a fresh baseline. Compare that marker on polling before reading a cursor; refresh a stale tab when its authenticated session changes. If a form modal or confirmation is open, defer polling/presentation until it closes (without advancing the position), rather than putting alert controls above an active dialog. Existing normal polling resumes custom overlays within 15 seconds; native dialog close triggers an immediate check.

Approved follow-up: preserve a currently visible bar across same-tab page navigation/reload, including its grouping and remaining eight-second display budget. Save a short-lived handoff in the existing user/login-scoped session storage on pagehide; consume it on the next page. Loading time does not use the display budget. Dismissed, acted-on and expired bars must not return, including with Back/Forward. Keep hover/focus/hidden-page pauses. This reuses browser storage rather than changing navigation or adding server state. Builder decision: discard handoffs older than one minute so a restored closed tab cannot replay an old toast.

Approved offline follow-up (supersedes initial-history suppression): show eligible unread notifications that have never been delivered to the bar on the next customer login, including existing pending approvals. Persist a separate nullable `bar_shown_at` on Notification; never use is_read as the delivery receipt. GET remains read-only and returns all pending eligible events, independent of the transient cursor. A customer-only CSRF-protected POST acknowledges the exact signed batch after the bar is rendered. Include all batch IDs in that signed receipt even when only the newest 20 item bodies are serialized. Retrying a receipt is idempotent. Retain an unconfirmed receipt per user in session storage and retry it before fetching another batch to prevent duplicate grouping on a temporary acknowledgement failure. Preserve grouping at two, navigation handoff and the existing timer. Account-owned receipts persist across login/browser changes. Concurrent delivery in multiple tabs is best effort until a receipt reaches the server; do not claim transactional exactly-once display. Existing unread eligible records receive one delivery because the former version did not store their display history.
